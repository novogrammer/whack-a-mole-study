# whack-a-mole-study ゲーム仕様

本書は、最初の試作範囲を相談するための仕様案です。ユーザーの方針を「確定方針」、実装前に相談したい提案を「仮案」として区別します。仮案の数値は調整の出発点であり、決定事項ではありません。

## 1. 目的

広告キャンペーン向けのカジュアルWebゲーム制作を想定し、Vite + TypeScript + Phaserによる開発を学ぶ。

古典的なモグラ叩きをベースに、オリジナルキャラクターを叩いたときの表情や動きを楽しめるゲームを目指す。最初は短いゲームループで、タッチ操作の気持ちよさとリアクションの分かりやすさを検証する。

キャンペーンへの組み込み、公開、計測などは今回の試作範囲に含めない。

## 2. 確定方針

- スマートフォンの縦画面を主な対象とし、タッチ操作を基本にする。
- PCでもマウスで動作確認できるようにする。
- キャラクターの設定・世界観は後から決める。
- 最初は図形などの仮グラフィックを使用する。
- 基本ルールは一般的なモグラ叩きに準じる。
- 表情・動き・効果音など、キャラクターの演出を重視する。
- フェイントや特殊行動は、基本ループの検証後に検討する。
- Phaserの標準機能をできるだけ活用する。
- ゲーム部分はPhaserで実装し、必要に応じて周辺UIをHTML/CSSにする。
- 複雑な仕組みや過度な共通化を避け、小さく段階的に実装する。

## 3. 最初の試作範囲（仮案）

### 基本ルール

| 項目 | 仮案 | 検証したいこと |
| --- | --- | --- |
| プレイ時間 | 30秒 | 短時間で繰り返し試せるか |
| 穴の配置 | 3列 × 3行、合計9個 | スマホで狙いやすい間隔にできるか |
| キャラクター | 1種類 | 仮の表情・動きだけでも反応が伝わるか |
| 同時出現数 | 最大1体 | 入力とリアクションを落ち着いて確認できるか |
| 出現位置 | 空いている穴からランダム | 盤面全体の操作感を確認できるか |
| 出現までの待ち時間 | 前のキャラクターが完全に隠れてから400〜800ms | 待ちすぎず、反応も見届けられるか |
| 叩ける時間 | 1,000ms | 初見でも狙って叩けるか |
| 得点 | 命中1回につき1点 | 成功したことがすぐ分かるか |
| 空振り・見逃し | 減点なし、プレイ継続 | 入力の気持ちよさに集中できるか |
| 難易度 | 1プレイ中は固定 | 調整前後の感触を比較できるか |

最初はコンボ、ライフ、ランキング、ステージ進行を設けない。出現頻度を上げる調整は、リアクションを見届けるテンポとのバランスを確認してから行う。

### 最小ゲームループ

1. 待機画面で「スタート」を押す。
2. スコアを0、残り時間を30秒にしてプレイを開始する。
3. キャラクターがランダムな穴から出現する。
4. 叩ける間にタップすると、加点し、命中リアクションを表示して穴に戻る。
5. 叩かれずに時間が過ぎたら、見逃しリアクションを表示して穴に戻る。
6. 残り時間がある間は、待ち時間を挟んで出現を繰り返す。
7. 制限時間になると入力と出現を停止し、結果を表示する。
8. 「もう一度」でスコア・タイマー・キャラクター状態を初期化して再開する。

## 4. 画面構成（仮案）

画面遷移は「待機 → プレイ → 結果 → 再プレイ」とする。別ページへの移動はせず、同じ画面内で表示を切り替える。

| 状態 | 表示内容 | 主な操作 |
| --- | --- | --- |
| 待機 | 仮タイトル、短い遊び方、スタートボタン | スタート |
| プレイ | 上部に残り時間とスコア、中央に3 × 3の穴 | キャラクターをタップ |
| 結果 | 最終スコア、もう一度ボタン | 再プレイ |

配置イメージ：

```text
┌────────────────────┐
│ 残り時間    スコア  │
│                    │
│    ○    ○    ○     │
│                    │
│    ○    ○    ○     │
│                    │
│    ○    ○    ○     │
│                    │
└────────────────────┘
```

- 盤面は縦画面の中央に収め、HUDと重ねない。
- 端末の画面比率やセーフエリアに合わせ、ボタンや穴が画面外に出ないようにする。
- 基準サイズは幅390 × 高さ690程度を仮案とし、縦横比を保って拡縮する。
- PCや横画面では、縦長の盤面を中央に表示して余白を設ける。初回は横画面専用の配置を作らない。
- 実際の穴の大きさ・間隔は、小さいスマホ画面で確認して調整する。

## 5. 入力・判定（仮案）

- タッチ開始時・マウスボタンを押した時点で判定する。押し続けても連続加点しない。
- 出現アニメーションの終了から退場開始までを「叩ける時間」とする。
- 判定範囲は見えているキャラクターの周囲を含む固定領域とし、隣の穴と重ならないようにする。
- 命中した瞬間に叩けない状態へ切り替え、同じ出現に対して加点できるのは1回だけとする。
- 複数の指や連打があっても、命中済み・退場中のキャラクターは再加点しない。
- 穴だけの場所やキャラクターのいない場所を叩いても、スコアは変えない。
- ゲーム領域内では、通常のプレイ操作でページのスクロールや文字選択が起きないようにする。
- 待機中・結果表示中・一時停止中は、盤面の入力を受け付けない。
- 制限時間に達している入力は無効とし、終了後に予約された出現・加点が実行されないようにする。

## 6. キャラクターの状態とリアクション（仮案）

キャラクター名や世界観を決めず、「穴から出る仮キャラクター」として検証する。

| 状態 | 仮の見せ方 | 次の状態 |
| --- | --- | --- |
| 隠れている | 穴だけを表示 | 出現中 |
| 出現中 | 約150msで上に移動、通常の表情 | 叩ける状態 |
| 叩ける状態 | 通常の表情で待機 | 命中、または見逃し |
| 命中 | 約250ms、驚いた表情・一瞬つぶれる動き・小さなヒット表示 | 退場中 |
| 見逃し | 約150ms、別の表情に変える | 退場中 |
| 退場中 | 約150msで穴へ戻る | 隠れている |

仮グラフィックは円や楕円、目・口などで構成し、素材制作を待たずに動きを試せる形にする。穴の手前へ不自然にはみ出さないよう、表示順や隠れ方も確認する。

命中時は表情・形の変化とスコア更新をすぐに返す。大きな画面揺れや長い停止演出は初回には入れず、次の操作を妨げないリアクションを優先する。

### 効果音の扱い

効果音は重視するが、最初の無音の試作で入力と動きが成立した後に追加する案とする。次の段階で仮の命中音を入れ、必要に応じて出現音・終了音も検討する。

音を追加する段階では、開始操作を起点とした再生とミュート操作を用意し、無音でも成功・失敗が分かる状態を維持する。

## 7. 時間管理と中断（仮案）

- ゲーム時間はフレーム数ではなく経過時間で管理する。
- 別タブへの移動や端末の画面ロックなどで非表示になった場合は、進行・出現・リアクションを一時停止する。
- 戻ったときは再開ボタンを表示し、操作してから同じ状態・残り時間で続ける。
- 終了時は新しい出現と入力を止め、残っているキャラクターを片付けて結果を表示する。
- 再プレイ時には前回のタイマーやイベントを残さない。
- ページ再読み込みによるプレイ状態・スコアの保存は初回には行わない。

## 8. 技術構成

### リポジトリの現状

初回確認時点では、`package.json`にVite・TypeScript・Phaserが登録されている。`src/main.ts`はCSSの読み込みのみで、ゲームは未実装。本書の作成では依存関係やアプリケーションコードを変更しない。

### 実装時の構成案

- Viteを開発・ビルドに使用し、TypeScriptで実装する。
- Phaser側で盤面、キャラクター描画、入力、アニメーションを扱う。
- 入力、時間、Tween、サウンド、拡縮などは、採用バージョンの標準機能を確認して利用する。
- 固定カメラとし、物理エンジンは初回には導入しない。
- シーンは最小限にし、待機・プレイ・結果のためだけに細かく分割しない。
- 得点・残り時間・命中可否などのルールは、小さなTypeScriptの状態管理にまとめ、描画用オブジェクトと分ける。
- 穴の数、出現間隔、各状態の時間などは、調整用の定数としてまとめる。
- 汎用フレームワーク、複雑なイベント基盤、追加UIフレームワークは導入しない。

周辺UIは、待機・結果・再開のボタンやテキストをHTML/CSSにする案とする。スコア・残り時間も含め、実装前に表示担当を決め、同じ情報を両方で管理しない。見た目の状態はゲームの状態から更新する。

## 9. 初回では扱わないこと

- オリジナルキャラクターの正式な設定、名称、世界観、完成イラスト
- フェイント、複数同時出現、叩いてはいけない対象、特殊行動
- コンボ、難易度上昇、ライフ、アイテム、ステージ選択
- ランキング、ユーザー登録、サーバー連携、永続保存
- 広告配信、キャンペーンへの組み込み、アクセス解析、公開・デプロイ
- 本格的な素材制作や大量のアニメーション

## 10. 段階的な進め方と確認基準

### 段階1：仕様の相談（今回）

本書をもとに初回ルール、画面配置、命中リアクションを相談する。この時点ではゲームを実装しない。

### 段階2：最小ゲームループ

合意した範囲で、仮グラフィックを用いた開始・出現・命中・見逃し・終了・再プレイを実装する。

確認すること：

- スマホのタッチとPCのクリックで狙った対象を叩ける。
- 命中時に1回だけ加点され、見た目の変化がすぐに分かる。
- 見逃した場合も次の出現へ進める。
- 終了後には加点されず、再プレイすると前回の状態が残らない。
- 画面外への移動で停止し、復帰後に再開できる。
- 小さいスマホでも盤面・HUD・ボタンが重ならず、縦画面全体を操作できる。

### 段階3：リアクションの調整

出現速度、叩ける時間、表情、つぶれる動き、退場の間を、一度に変えすぎず比較する。仮の命中音とミュートを追加し、スマホ実機でも音と入力の感触を確認する。

### 段階4：拡張を選ぶ

操作感が成立してから、同時出現、フェイント、特殊行動などを1つずつ検討する。各拡張では、反応を見る楽しさ、狙いやすさ、ルールの伝わりやすさを確認する。

## 11. 次に相談したいこと

1. **初回ルール**：30秒・3 × 3・同時1体・命中1点・減点なしで始めるか。
2. **命中リアクション**：驚いてつぶれる動きを出発点にするか。かわいさ・コミカルさなど、仮に寄せたい方向があるか。
3. **音の追加時期**：最小ループの検証後に追加するか、初回実装に短い命中音も含めるか。

キャラクター設定や特殊行動の詳細は、この3点と最小ループの手応えを確認してから決める。
