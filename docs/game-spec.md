# whack-a-mole-study ゲーム仕様

相談しながら育てるための仕様書。決まった方針と、これから試す仮案を分けて記載する。

## 1. 作りたい体験

広告キャンペーン向けのカジュアルWebゲーム制作を想定し、Vite + TypeScript + Phaserで開発を学ぶ。

古典的なモグラ叩きをベースに、オリジナルキャラクターの表情・動き・効果音を楽しめるゲームを目指す。まずは仮グラフィックで、狙って叩く操作感と、叩いたときのリアクションを確かめる。キャラクター設定や世界観は、相談しながら決める。

スマホの縦画面・タッチ操作を基本とし、PCではマウスでも確認できるようにする。

## 2. ゲームの単位

### プレイ

スタートから結果表示までを「1プレイ」とする。出現開始の譜面は32秒・40チャレンジとし、最後のモグラの帰還を待ってプレイを終了する。

### チャレンジ

**モグラが穴から出始めて、穴へ戻りきるまでの一連の動き**を「1チャレンジ」とする。叩かれた場合のリアクションも、そのチャレンジに含める。

120 BPM・4拍子の16小節を、八分音符128枠で表す。1枠は250ms、各行は4小節・8秒。`1`は1体の出現開始、`0`は出現開始のない枠を表す。

```text
1000 0000 1000 0000 1000 0000 1000 0000
1000 0010 1000 0010 1000 0010 1000 0010
1000 1010 1000 1010 1000 1010 1000 1010
1010 1000 1111 1000 1010 1000 1111 1000
```

各8秒区間の出現数は4・8・12・16体、合計40体。出現開始時刻は固定し、場所だけをランダムに割り当てる。開始時刻が異なっても前のモグラが残っていれば同時に見える。

## 3. 1チャレンジの流れ

### 通常の動き

```text
出てくる → 出きった位置で約1秒停止する → 引っ込む → 完了
```

決まっていること：

- 出てくる途中から叩ける。
- 出る速度と引っ込む速度は同じにする。
- 出きった位置で約1秒停止する。

出入りの所要時間は、片道150msを仮案とする。この場合、通常の1チャレンジは約1.3秒となる。

### 叩いたとき

```text
出現中または停止中に命中 → リアクション → 穴へ戻る → 完了
```

命中したらその場で反応を返す。仮案は「驚いた表情と一瞬つぶれる動き」で、リアクションの長さや戻り方は実際に見て調整する。

叩けるタイミングは、このチャレンジの流れに沿って定義する。今回の実装では、出現中と停止中に叩ける。引っ込む途中の判定は今後の相談事項として残す。

## 4. 盤面と画面

盤面は、手前のモグラが後ろの穴やモグラに重なるくらいの配置を目指す。見た目もタップの判定範囲も重なりを許容し、仮グラフィックで大きさと間隔を確かめる。

穴は楕円とし、その下半分の輪郭に沿った地面色の図形を手前に重ねる。地面の幅は穴と同じ幅に絞り、隣の穴を覆わないようにする。モグラは地面より上と穴の内側で見え、手前の縁より下は地面に隠れる。タップ判定も見えている範囲に合わせる。

仮のモグラは顔の形と位置を保ち、その後ろに下方向へ続く胴体を描く。停止中や命中リアクション中も胴体の下端が地面に隠れ、穴から体がつながって出ている見え方にする。

タップの判定範囲は、見えているモグラを基準に、スマホで狙いやすい大きさへ調整する。

画面構成の仮案：

| 画面 | 内容 |
| --- | --- |
| 待機 | タイトル、短い遊び方、スタートボタン |
| プレイ | 残り時間、スコア、穴とモグラ |
| 結果 | 最終スコア、タイトルへ戻るボタン |

スマホでは縦画面に収め、次の基準でレイアウトする。

| 項目 | 方針 |
| --- | --- |
| ブレークポイント | 768px未満はSP表示、768px以上はPC表示 |
| SP | デザイン基準幅375px。中央コンテンツは画面幅に合わせて拡縮する |
| PC | デザイン基準幅1200px。中央コンテンツは幅500pxで中央配置する |

PCの1200pxはデザインの基準幅とし、中央コンテンツは768px以上で幅500pxを保つ。

## 5. 最初に作って試す内容（仮案）

### 現在の実装段階：固定リズムのプレイとスコア・画面表示

3列 × 3行の9マスに仮のモグラを配置する。スタート時に譜面から40件の進行表を生成する。各モグラは「150msで出現 → 約1秒停止 → 150msで帰還」と動く。最後の出現は31秒で、通常の帰還完了は32.3秒、命中のタイミングによっては約32.6秒まで続く。32秒を過ぎて全チャレンジが完了したら結果を表示する。「タイトルへ戻る」で待機画面へ戻り、改めて「スタート」を押すと場所を再抽選してプレイを開始する。

待機中は仮タイトル・短い遊び方・スタートボタンを表示する。プレイ中はスコアと残り時間、終了後は最終スコアと「タイトルへ戻る」を表示する。タイトルへ戻る操作ではゲームを開始しない。画面のテキスト・ボタンはHTML/SCSSで構成し、盤面の上に表示を切り替えて配置する。

命中1回につき1点、満点は40点とする。Challengeが命中を受け付けたときだけContextの`addScore(1)`を呼び、Sceneが合計を管理する。連打で同じチャレンジが重複加点されることはなく、空振り・見逃しでは得点を維持する。

残り時間は32秒からの秒単位の切り上げ表示とし、最後の帰還待ちでは0秒を表示する。0秒になった後でも、残っているチャレンジの出現中・停止中は叩けて加点される。全チャレンジが完了してから最終スコアを表示する。再プレイ時はスコアを0、残り時間を32秒へ戻す。

出現中・停止中に見えているモグラをタップまたはクリックすると命中する。命中時は通常の動きを止め、目を×にして口を開き、横に広がって縦につぶれる短いリアクションを返してから穴へ戻る。1チャレンジにつき1回反応し、完了後は通常の表情で再実行できる。

リアクションは片道90msの変形と120msの停止を仮案とし、帰還は残りの距離に合わせて通常と同じ移動速度にする。

命中したタップ位置に、既存リアクションと重ねて小さなヒットエフェクトを出す。星を100ms表示した後、中心付近に短い線が集まった放射線の画像へ切り替え、画像全体を200msかけて拡大・フェードアウトする。全体で300msとする。線の長さ・太さ・間隔は画像全体の拡大に合わせて変わる。空振りや、命中済みのモグラへの再タップでは出さない。

エフェクト素材は`src/assets/fx/hit-star.svg`と`hit-rays.svg`の2枚。どちらも128 × 128px、透過背景、中心位置を揃えた仮素材とする。モグラの位置や表情を動かすTweenとは別に、盤面の前面へ表示する。

指で隠れにくいよう、星・放射線の表示サイズは初期案の2倍とする。素材に対する倍率は、星が0.56 → 0.8、放射線が0.64 → 1.44。表示位置はタップ位置のままとする。

### 最小ゲームループの仮案

| 項目 | 出発点 |
| --- | --- |
| 穴の数 | 3列 × 3行の9個 |
| 出現位置 | ランダム |
| チャレンジの進行 | 同じマスの予約を重ねず、別マスでは同時出現を許容する |
| チャレンジ数・時刻 | 32秒の固定譜面から40件。1枠250ms |
| 得点 | 1チャレンジの命中につき1点 |
| 空振り・見逃し | スコアを維持して続行 |
| グラフィック | 図形と簡単な目・口による仮キャラクター |

「待機画面 → スタート → チャレンジを繰り返す → 結果 → タイトルへ戻る」という最小ループを作り、出入りの速さ、停止時間、チャレンジの間隔、命中リアクションを確かめる。

スコアの集計・表示、残り時間の表示、待機画面と結果表示は実装済み。効果音とキャラクター素材・演出の作り込みは後回しとし、当面は現在の仮グラフィックと簡単な命中リアクションで進める。

## 6. 技術方針

Vite + TypeScript + Phaserを使用する。Phaserの標準機能を活用し、ゲーム部分をPhaser、必要な周辺UIをHTML/SCSSで実装する。

中央コンテンツのSCSSは、提示された`sp-and-pc-block`の方式で、SPデザイン上のpx値からSP用のvw値とPC用のpx値を生成する。

- SP：`SPデザイン上のpx値 ÷ 375px × 100vw`
- PC：`SPデザイン上のpx値 × (500 ÷ 375)`

例えばSPデザイン上の75pxは、SPでは20vw、PCでは100pxとなる。`mq-pc`の切り替え幅は768pxとする。

Phaserのゲーム座標は幅375を基準とし、Canvasは750 × 750pxで描画する。カメラを2倍に拡大して座標を保ち、盤面全体を中央コンテンツの表示幅へ拡縮する。SCSSの寸法変換はHTMLのUIに使い、盤面とUIの表示スケールを揃える。

プレイとチャレンジの状態を整理し、描画やアニメーションへ反映する。時間や間隔は調整しやすい定数にまとめ、試作に合った小さな構成から始める。

プレイ開始時にスケジュールを生成し、設定配列を`challengeParams.map(params => new Challenge(this, params))`の形でインスタンス化する。`challenges`を1プレイの進行表として持ち、開始時刻順に更新する。これにより、時間更新が飛んでも同じマスの前のチャレンジを先に完了できる。

`Challenge`クラスが進行段階の`phase`と、命中済みかを表す`isHit`を管理する。`phase`は`idle`（開始前）、`emerging`（出現中）、`waiting`（停止中）、`returning`（帰還中）、`completed`（完了）とする。完了後も命中結果を保持し、再実行時は進行表を新たに生成して配列を作り直す。

Sceneは`ChallengeContext`を実装し、各`Challenge`に`onUpdate(elapsedMs)`で時間、`onTap(elapsedMs)`でタップを渡す。`Challenge`自身が時間と入力から進行を決め、Contextの`emergeMole()`・`holdMole()`・`showHitReaction()`・`returnMole()`・`hideMole()`を呼んで演出を依頼する。SceneはMoleへの操作の振り分けを担当する。

`Mole`は1マス分の描画・Tween・当たり判定を担当し、Sceneは`moles`配列として持つ。現在は3列 × 3行の9個とし、手前の行が前面に描かれるようにする。`ChallengeParams`の`moleIndex`で対象を指定し、Contextの各操作へ渡す。Sceneは`moles[moleIndex]`に操作を委譲する。

`emergeMole(moleIndex, durationMs, onTap)`には、その`Challenge`のタップ用コールバックを渡す。Moleは出現時にリスナーを登録し、位置の当たり判定を通ったタップを通知する。Sceneは経過時間を付けてコールバックへ渡し、命中の受付可否は`Challenge`内部で判断する。リスナーはMole内部で命中リアクション・帰還・非表示・破棄時に解除し、次の出現では新たに登録する。

`canHit()`は「出現中または停止中、かつ未命中」を判定する。命中時は`isHit`を更新し、その時点の`phase`のまま通常の進行と移動を止めてリアクションを返し、終わったら帰還へ進む。

出現・停止・命中リアクション・帰還の時間は`Challenge`側で管理し、SceneのTween完了通知で状態を操作しない。Moleは演出の依頼を受ける際に直前のTweenを解除し、出現と帰還は独立したTween、命中時のつぶれて元に戻る動きはTweenの`yoyo`で表現する。

### スケジュールの生成

1件の予約時間は、出入り・停止・命中リアクションを含む最大所要時間で確保する。現在は`150 × 2 + 1,000 + 90 × 2 + 120 = 1,600ms`を確保し、実際に早く終わっても次のチャレンジの開始時刻は変えない。予約区間は終了時刻と次の開始時刻が一致してよい。

譜面を先頭から読み、`1`のある枠について次を行う。

1. 枠番号 × 250msを開始時刻とする。
2. その時刻に予約が空いているマスからランダムに1個選ぶ。
3. 開始時刻から最大所要時間までを、そのマスの予約とする。

時刻順に割り当てるため、生成中はマスごとの直前の予約終了時刻を管理すればよい。空きマスがなければ時刻をずらさず生成エラーとする。予約管理は生成関数内で完結し、MoleやChallengeに予約表を持たせない。

以前の、件数を各マスへ配り余白をランダム分割する生成方式は廃止する。

## 7. これから相談すること

- 引っ込む途中も叩けるようにするか。
- 固定譜面で試し、各区間のリズムや難易度をどう調整するか。
- 命中したチャレンジの長さをどうするか。リアクション後に早く完了するか、元の終了予定まで使うか。
- 穴の数、得点、命中リアクションなどの仮案を出発点にしてよいか。

まずはこの単位で基本ループを相談し、操作感を確かめながら表情・動き・音を育てる。フェイントや特殊行動も、チャレンジのバリエーションとして検討する。
